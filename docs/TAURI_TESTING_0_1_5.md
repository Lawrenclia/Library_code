# 0.1.5 WOS 等待与界面卡顿修复

本版修复代码中发现的阻塞和重复工作。完整名单、检索记录、待确认写入和名单版本仍保存、显示，不删减来源来降低开销。按用户要求只编译打包，不运行测试或操作真实 WOS/机构库；以下步骤供用户自行核对，不是已通过的业务验收。

## 本版修改

- 完整工作台快照在后台线程读取，避免名单与历史查询占用桌面 UI 线程。任务、检索历史、未知操作和名单版本在一次 SQLite 只读事务中批量读取；原先每条任务的三个独立查询改为整个名单的四次查询，保留所有记录和事件顺序。
- 前端合并连续状态事件，同一时刻只请求一份工作台快照；读取期间发生的新事件会触发后续读取，旧响应不会覆盖新响应。
- WOS 加载中不扫描全部题录链接和结果计数，完整记录页不扫描参考文献与结果计数。等待循环的站点错误检查不再读取触发布局计算的整页 innerText。实际控件可见性、唯一目标和完整记录导出仍独立检查。
- 完整记录页的题名与本次目标准确一致且唯一导出按钮已出现时，不再因其他区域的持续忙碌标志无限等待；没有这两项明确页面依据时仍保留加载判断，文件身份仍须解析核验。
- 原生检索前八秒每 500 毫秒检查，之后每 1500 毫秒检查，减少慢页面的重复扫描。慢页面不能据此判定零结果；总等待截止时间使用单调时钟。
- 打开唯一结果后，旧列表或旧详情仍短暂显示时继续等待目标详情，不再立即报“仍停在结果列表”。目标改变、多个结果或身份冲突不会自动选择或再次导航。
- 返回或刷新检索页时不再盲等固定两秒就派发长命令，而是通过只读短探针确认新文档和唯一单行表单已挂载，最多等 25 秒。原生探针使用文档内临时标记区分刷新前后，防止把旧页面的就绪状态误当新页面；没有新增自动检索提交。
- 主窗口显示检索准备、等待结果、打开目标、导出设置和等待下载的实际阶段及已等待秒数；轻量进度事件不触发整份名单刷新。
- 在派发检索前和结果轮询之间检查暂停。暂停检索后任务回到待继续、队列保留当前位置，不记录成普通失败或跳到下一篇。单次页面准备有原来的 35 秒上限，只读结果探针有 5 秒上限；暂停不是强杀浏览器。已经发出的下载继续等真实完成回执，最多 40 秒，结果未知保留原回执且不自动重发导出。

## 用户自测顺序

1. 从 [Windows EXE](https://github.com/Lawrenclia/Library_code/actions/workflows/windows-exe.yml) 下载 0.1.5 的 Artifacts，解压安装。应用左侧底部应显示 **v0.1.5 测试版**；旧安装程序不会因 Git 更新自动升级。
2. 打开自己的工作目录和名单。自行登录内置 WOS，先使用一篇已知能定位的论文。检查主窗口可切换任务、阶段文字更新，最终得到真实完整记录 TXT；有多个结果时应待人工核对。
3. 用一篇真实无结果论文核对零结果与失败区分。连续普通失败应继续原范围，页面或机构访问故障保留未执行项，不重发未知下载。
4. 等待检索结果期间点击暂停，检查原队列位置保留。继续时核对原名单范围、已保存文件和新查询记录；暂停本身不证明已完成检索。
5. 详情加载较慢时应等待原目标，不重复导航、搜索或导出。已发出下载期间暂停，应保留或等完成回执，不将文件仍在传输当作失败重下。
6. 保留出现问题的 SA ID、版本、具体等待阶段、报错、来源报告和原文件。网络、WOS 服务响应和机构访问的实际耗时仍由站点决定，本版没有经真实站点计时验收。

本版没有修改上传、导入、推送、认领和 SA 已处理的完成条件。完整目标及未现场验收范围见 [重构规范](TAURI_REBUILD_GOAL.md)和 [交付状态](TAURI_ACCEPTANCE_STATUS.md)。
